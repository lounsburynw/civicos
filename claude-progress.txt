## Session 315: preflight_checks + Storage Architecture Discovery

**Date:** 2025-12-21
**Item:** preflight_checks (city_onboarding > validation)
**Priority:** P1

### Summary
Implemented `source.validate()` method on all DataSource clients. Then discovered critical gap: Pipeline fetches meetings but has no persistence layer.

### Critical Discovery: Pipeline Has No Storage

Tested `civic-bootstrap san-rafael --skip-index`:
- discover: 850 items (health check)
- ingest: 17 meetings fetched into memory
- **Problem:** Meetings are discarded when process exits - no disk write!

### Architecture Decision for Next Session

**4-stage pipeline:** discover → ingest → store → index

**Two protocols in `civic/storage/`:**
```python
class StorageBackend(Protocol):  # Primary storage (source of truth)
    def save_meetings(self, meetings: List[Meeting]) -> int
    def get_meetings(self, jurisdiction_id: str) -> List[Meeting]

class VectorBackend(Protocol):  # Search index (derived)
    def index(self, meetings: List[Meeting]) -> int
    def search(self, query: str, k: int) -> List[SearchResult]
    def rebuild(self, storage: StorageBackend) -> int
```

**Key principle:** Index reads from StorageBackend, not memory. Vector index is always derived from primary storage.

**Implementations:**
- StorageBackend: SQLiteStorage (pilot), PostgresStorage (scale)
- VectorBackend: ChromaDBBackend (pilot), PgVectorBackend (scale)

**1. ValidationResult Dataclass** (base.py)
- `is_valid` - all checks passed, safe to proceed
- `config_valid` - config structure is correct
- `api_reachable` - API endpoint is accessible
- `errors[]` - critical errors (fail fast)
- `warnings[]` - non-blocking issues
- `check_duration_ms` - timing info
- `metadata` - platform-specific context

**2. DataSource Protocol** (base.py)
- Added `validate() -> ValidationResult` method signature
- Preflight check that fails fast before pipeline runs

**3. ProudCitySource.validate()** (proudcity.py)
- Checks: base_url (required, HTTPS), jurisdiction_id, source_id
- Checks: archives non-empty OR auto_discover enabled
- API check: hits `/meetings/` endpoint
- Archive validation: verifies each archive path is reachable (warnings)

**4. LegistarClient.validate()** (legistar.py)
- Checks: client_name required
- API check: hits `/bodies` endpoint

**5. CivicClerkClient.validate()** (civicclerk.py)
- Checks: subdomain required
- API check: hits `/Boards` endpoint

## Session 316: storage_backend_protocol

**Date:** 2025-12-21
**Item:** storage_backend_protocol (city_onboarding > orchestration)
**Status:** COMPLETE

### Summary
Created StorageBackend and VectorBackend protocols for the 4-stage pipeline:
discover → ingest → store → index

### Implementation

**StorageBackend Protocol** (`packages/civic/src/civic/storage/backend.py`):
- `@runtime_checkable` protocol for primary data persistence (SQLite, Postgres)
- Methods: `validate()`, `store_meetings()`, `get_meetings()`, `get_stats()`, `delete_meetings()`
- Dataclasses: `StorageStats`, `StorageValidationResult`
- Supports temporal versioning via `as_of` parameter

**VectorBackend Protocol** (`packages/civic/src/civic/storage/vector.py`):
- `@runtime_checkable` protocol for vector search (ChromaDB, pgvector)
- Methods: `validate()`, `index_from_storage()`, `search()`, `get_stats()`, `delete_index()`
- Dataclasses: `SearchResult`, `VectorStats`, `VectorValidationResult`
- Key design: `index_from_storage()` reads from StorageBackend, not memory

**Key Design Principle:**
Index reads from storage, not memory. This ensures:
- Data is persisted before indexing
- Re-indexing possible without re-fetching from source
- Clear separation of store and index stages

## Session 340: postgres_backend_implementation - PostgreSQL Storage Backend

**Date:** 2025-12-22
**Item:** postgres_backend_implementation (city_onboarding > orchestration)
**Priority:** P0 (IMMEDIATE)

### Summary
Created PostgresBackend class implementing the StorageBackend protocol. This proves the storage abstraction works for multiple backend implementations, enabling municipalities with existing PostgreSQL infrastructure to adopt Civic.

### Implementation

1. **PostgresBackend Class** (`packages/civic/src/civic/storage/postgres_backend.py`):
   - Full implementation of StorageBackend protocol (558 lines)
   - All 5 protocol methods: validate, store_meetings, get_meetings, get_stats, delete_meetings
   - Uses psycopg2 with RealDictCursor for dict-like row access
   - Temporal versioning via composite PK (id, valid_from) and valid_to column
   - Same schema as SQLiteBackend for data portability
   - `backend_type` property returns "postgres"
   - `get_stats()` includes `metadata={"backend_type": "postgres"}`
   - Database size via `pg_database_size(current_database())`

2. **Conditional Import Pattern**:
   - psycopg2 is optional - import fails gracefully with clear error message
   - `PSYCOPG2_AVAILABLE` flag controls runtime checks
   - Allows package to work without psycopg2 when only SQLite is needed

3. **Test Suite** (`packages/civic/tests/test_postgres_backend.py`):
   - 28 tests mirroring SQLiteBackend test structure
   - Tests skipped via `pytestmark` when CIVIC_TEST_POSTGRES_URL not set
   - Includes protocol compliance, CRUD operations, temporal versioning, Pipeline integration

4. **Package Export** (`packages/civic/src/civic/storage/__init__.py`):
   - Added PostgresBackend to public API
   - Available via `from civic.storage import PostgresBackend`

### Key Design Decisions

1. **Same Schema**: Both SQLite and Postgres use identical table structures:
   - city_states, meetings, agenda_items
   - Composite PKs for temporal versioning
   - Same indexes for query performance

2. **Connection-per-Request**: No connection pooling yet (suitable for pilot scale)

3. **ISO 8601 Datetime Strings**: Cross-backend compatibility for temporal queries

4. **Soft Deletes**: Temporal versioning means no data loss on delete

3. **Production readiness**: Postgres better suited for multi-user deployments
4. **Config-only migration**: Switch backends via environment variable

   - `BlobStats`: Statistics dataclass (total_objects, total_bytes, by_content_type)
   - `BlobValidationResult`: Preflight validation result (connected, writable, errors)

   - Filesystem-based storage for local development
   - Creates nested directory structures automatically
   - Stores metadata in memory (content types)

3. **R2Backend** (production):
   - Cloudflare R2 (S3-compatible) using boto3
   - 10GB free tier with zero egress fees
   - Factory methods: `from_env()` and `from_url()`
   - Full CRUD operations via S3 API

4. **Factory Function**:
   - `get_blob_storage(url)`: Auto-selects backend based on URL scheme
   - `r2://` → R2Backend
   - `local://` → LocalBlobBackend
   - Default → LocalBlobBackend("data/blobs")

5. **Environment Configuration** (`.env.example`):
   - `BLOB_STORAGE_URL`: Storage URL (r2:// or local://)
   - `R2_ACCESS_KEY_ID`: R2 API token access key
   - `R2_SECRET_ACCESS_KEY`: R2 API token secret
